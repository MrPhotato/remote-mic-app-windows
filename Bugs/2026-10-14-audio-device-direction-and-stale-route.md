# 麦克风页面的播放设备列表与失效传送端

- 发现日期：2026-10-14
- 状态：故障链已定位，修复方案已形成；尚未修改运行配置或实现恢复
- 影响范围：Windows 安装版 0.2.11，源码 `79b1af6d02228045fa9ddf4213e92c63811786ba`；RC003 当前连接保留。
- 功能点：连接与语音、音频设备枚举、保存的端点恢复。
- 现象：Windows 已选 CABLE Output，麦克风高级列表仍显示 Speakers，应用显示传送错误。

## 现场证据

通过 Cua 后台快照读取原窗口，未点击设备、改变焦点或重启应用。
页面保存的端点为 `CABLE In 16ch (VB-Audio Virtual Cable)`，报“上次选择的输出端点当前不可用”。
当前列表有两个虚拟播放端 `CABLE In 16 Ch (2- VB-Audio Virtual Cable)`、
`Speakers (2- VB-Audio Virtual Cable)`，另有一个 Realtek 播放端。

公开 Windows 设备查询确认 `CABLE Output (2- VB-Audio Virtual Cable)` 存在。
公开 WinRT `MediaDevice.GetDefaultAudioCaptureId` 的只读结果：Default 为 CABLE Output，
Communications 为内置麦克风阵列。此事实不证明 Codex 的实际设备选择，未访问其私有配置。

当前进程日志：09:50:36（UTC+8）恢复保存端点失败，
`error_code=endpoint_identity_mismatch reason=persisted_endpoint_missing_or_changed`。
09:53:18–09:53:58 的 9 次语音启动均为 `endpoint_not_selected`。
枚举成功，活动播放端共 3 个，其中虚拟端 2 个；不是枚举 API 失败或 VB-CABLE 未安装。
本地诊断尾部副本 SHA-256：`a7c5fa9a78c9a49dff2ecb726ce04e8254e44f856dd02b2c97fb6659062fa1d1`。

## 已确认的实现边界

- `audio.rs::list_endpoints` 使用 `Direction::Render`，所以列出播放端，不会列出 CABLE Output 录音端。
- 主界面“目标应用使用的麦克风 / CABLE Output”是固定说明，不是检测结果，也没有读取目标应用的选择。
- 保存端点恢复要求 ID 与名称匹配；当前旧 ID 不在活动列表。此次未核实端点变化的历史诱因。
- 刷新列表保留已有选择，不会修复失败的音频流；因此列表已更新与实际传送仍失败可以同时出现。
- 不能直接把现有枚举改成 Capture：其选择路径用 Render 打开流并写入遥控器声音。

## 修正边界与验证

### 先前正常与本次失败的对照

用户补充此前一直能自动恢复；完整历史日志支持该反馈。同一源码 `79b1af6`、同一版本
0.2.11 在 10 月 8 日 13:36:02 和 10 月 12 日 09:52:22（UTC+8）均记录
`action=restore terminal_result=passed`，10 月 14 日 09:50:36 首次记录本次端点身份不匹配。
当前实际读取的普通用户配置与 0.2.11 安装前备份的音频 ID 和名称相同；该配置最后修改于
9 月 28 日。不能将本次故障解释为用户此前从未配置好，或这版应用从未正常恢复。

公开 PnP 读取确认，保存 ID 对应的旧端点仍有历史节点，但 `IsPresent=false`。
当前带 `2- VB-Audio` 的三个端点对应不同的父节点，最新到场时间均为 10 月 13 日
10:34:22（UTC+8）；首次安装时间却为 9 月 21 日。到场时间不等于驱动安装时间，
也不能据此断言用户重装驱动、Windows 更新或某个程序改坏了设备。
端点活动身份变化的具体触发因素仍未知。

代码还确认了恢复缺口：启动只尝试恢复一次，失败后保留 ID 但没有可用音频流；
后续列表刷新和状态轮询都不重新打开音频流，语音开始也不触发恢复。
有旧 ID 时前端不会自动选择新 CABLE；即便原 ID 再次出现，同 ID 的“选择”按钮也仍被禁用。
因此偶发的设备不可用可能形成持续故障，日志中的 `retryable=true` 不代表已有重试调度。

另有 Codex 包缓存内的历史配置副本，其音频选择与普通用户文件不同；当前窗口及日志与
普通用户文件一致，且普通用户文件未变化，不能将历史副本差异认作这次配置切换的证据。
全文日志副本 SHA-256：`3bc23001ee502dade63249d47f04fc1b654015fd1a59c08e4109dd9b53e11b71`。

### 待修复边界

应分开检测并展示录音端 CABLE Output 和写入端的状态，避免固定文字冒充已检测/已选中。
高级内部传送列表应明确用途，普通扬声器不应混在麦克风选择中。
失效设置应明确展示不可用；重新绑定须确认对应虚拟线路，不能仅凭名称模糊匹配自动切到任意设备。
应分别覆盖原端点暂时不可用后恢复、端点身份变化、存在两个虚拟播放端的情况，
不能用仅修改 UI 或只重试同一个已消失 ID 宣称本次故障修复。
VB-CABLE 参考：[官方说明](https://vb-audio.com/Cable/)。

## 设备层最终核对与方案（2026-10-14）

### 已证实的故障链

1. 公开 PnP 查询发现 3 个 `VB-Audio Virtual Cable` MEDIA 设备实例，均为
   `VBAudioVACMME` / 3.3.1.7；其中 1 个正常、2 个 `ProblemCode=10`。
   两个失败实例的 `ProblemStatus=0x80000011`（`STATUS_DEVICE_BUSY`）。
2. 应用保存端点的父设备正是失败实例；当前活动虚拟端点属于另一个正常实例。
   这是设备启动失败状态，不足以认定某个录音应用独占了音频。
3. 独立 Core Audio 只读探针 `GetDevice(savedId)` 成功，`GetState` 为
   `DEVICE_STATE_NOTPRESENT`。旧 ID 仍能解析，不能把“未在 active 枚举出现”
   直接等同于 ID 被重建。全部 VB 端点中 3 个 active（2 render、1 capture），
   3 个 not_present（2 render、1 capture）。
4. 程序只在 active 列表找保存 ID，记录身份不匹配，保留配置但没有音频流；
   刷新列表不重建流，同 ID 重试入口也被禁用。这使设备故障持续表现为无法语音。

系统安装日志在 10 月 13 日 10:34:24、10:34:26（UTC+8）有 Windows servicing
`TiWorker.exe` 触发的 `Enable Device Install` 记录，涉及旧父设备，结束状态 SUCCESS。
时间紧邻正常实例端点的到场，但该记录不证明是哪次更新造成 Code 10，也不能证明
重复实例如何产生或为何切换。驱动启动失败与应用恢复缺口已经有直接证据，外部触发细节仍未知。

### 建议处置与实现顺序

- **当前现场的最小恢复**：诊断已保留后，通过应用重新绑定当前正常 VB-CABLE 实例的
  播放入口，保留 CABLE Output 录音端及系统扬声器设置。原来使用 16ch 入口，可先验证
  正常实例中的对应入口；验证实际声音到目标应用后才算恢复。此步骤本轮未执行。
- **同一端点恢复**：保留选择和恢复意图；订阅公开设备状态通知，在音频 worker 中处理
  可用事件和有限退避，失败流释放后重新创建。回调只入队，不能阻塞或重建流。
  不在按住语音键的实时路径中等待设备恢复，也不在恢复后播放旧会话队列。
- **设备身份或实例变化**：先读取保存端点的完整状态、父设备问题码，再判断是否有经过
  验证的同一线路；不能只重试旧 ID，不能按名称模糊匹配选任意 Speakers。
  当前两个 active render 是正常 VB-CABLE 的不同输入接口，不能按“数量为 2”认定有
  两根独立线。通过公开拓扑/设备属性确认实例，结合用户保存的接口偏好处理；不确定时
  明确展示候选供一次重绑定，不能偷偷改变系统默认设备。
- **界面**：麦克风区域枚举真实 capture、显示当前 Windows 默认角色；录音来源状态与
  内部 render 线路状态分开。新增明确的“重新检测并恢复线路”动作；失败时允许同设备
  重试。固定 CABLE Output 文字不得表示已检测/已选中；播放列表继续用于内部传送，
  不能直接改为 Capture 后交给现有 Render 开流函数。
- **日志**：区分 `not_present`、`disabled`、`unplugged`、`GetDevice` 失败、父设备
  问题码、恢复开始/结果、线路重新绑定及音频会话代次；不写端点 ID、路径或语音。

Windows 11 24H2+ 的公开 StableId 可评估作后续配置升级，但本机只读探针未能可靠解析
属性键；结果是“未查询”，不是“没有 StableId”。它不能作为本次已经验证的补救手段，
更不能保证将两个不同驱动实例视为同一条线路。方案不以它为前置条件。

### 验收要求与当前结论

- 只读事实：`passed`；证据见 [脱敏设备层报告](../Testing/evidence/audio-route-diagnosis-20261014.json)。
- 原端点暂时不可用后回来、正常改名、端点实例变化、多个虚拟接口的选择均须分别验证。
- 语音中失效须取消原会话并成对释放快捷键，恢复后仅接受新会话；不得播放旧队列。
- Windows 真机回验须包含闲置首用、文本实际出现、普通扬声器未改、真实麦克风默认角色显示。
- 运行配置修正、代码实现、端到端验证：`deferred`；本轮目标为定位及形成解决方案。
- 全程未修改驱动、系统音频选择、蓝牙、现有应用进程或连接。

- `passed`：窗口、当前版本、公开设备枚举、两类默认录音设备及同进程日志交叉核对。
- `failed`：当前保存的音频线路恢复和语音启动。
- `deferred`：UI 修正、虚拟线路重新绑定、遥控器音频到目标应用的端到端验证。
- 现场未改变：音频设备选择、系统默认音频、蓝牙、应用进程及连接。
